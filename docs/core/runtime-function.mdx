title: RuntimeFunction

A **RuntimeFunction** is a class with a `run()` method that Hercules calls when an execution request arrives from
Aquila. It is the implementation layer — all logic lives here.

```ts
import { Identifier, Signature, Name, OmitRuntimeFunction } from '@code0-tech/hercules';
```

## Overview

When `action.registerRuntimeFunction()` is called, Hercules automatically also registers a `FunctionProps` entry using
the same metadata. Apply [`@OmitRuntimeFunction`](./decorator-omit-runtime-function.mdx) to suppress this and register
the public definition manually via `action.registerFunction()`.

The descriptor stored in `action.runtimeFunctions` is documented on the
[RuntimeFunctionManager](./runtime-function-manager.mdx) page.

## `RuntimeFunctionClass`

```ts
type RuntimeFunctionClass<T extends RuntimeFunctionRunnable = RuntimeFunctionRunnable> =
  new () => T;
```

The constructor type accepted by `action.registerRuntimeFunction()`.

## Example

```ts
@Identifier('fibonacci_runtime')
@Signature('(n: number): number')
@OmitRuntimeFunction()
export class FibonacciRuntimeFunction {
  run(context: FunctionContext, n: number): number {
    if (n <= 1) return n;
    return this.run(context, n - 1) + this.run(context, n - 2);
  }
}
```

## Returning a sub flow function

A `run()` block may return a **sub flow function** instead of raw data. Hercules
registers its `run` internally and reports the function to Aquila as a sub flow
function result, so a later node of the flow can invoke it like any other sub flow.

Because nothing in the module definition describes a function that only comes into
existence at runtime, its name, description and I/O schema have to be declared with it.
The schemas are written as [Zod](https://zod.dev) schemas — the same way
[`@Schema`](./decorator-schema.mdx) describes a data type — and are converted to JSON
schemas while the result is sent:

```ts
import { z } from 'zod';
import { SubFlowFunctionDefinition } from '@code0-tech/hercules';

@Identifier('greeter_runtime')
@Signature('(greeting: STRING): TRANSFORM<STRING, STRING>')
export class GreeterRuntimeFunction {
  run(context: FunctionContext, greeting: string): SubFlowFunctionDefinition {
    return {
      name: 'greet',
      description: `Greets a name with "${greeting}"`,
      inputSchema: z.object({ name: z.string() }),
      outputSchema: z.string(),
      run: (name) => `${greeting} ${String(name)}`,
    };
  }
}
```

The input schema is an object keyed by parameter name, the output schema describes the
value the function returns. Each is generated from its own side of the zod schema —
the input schema from the schema's input side, the output schema from its output side
— so a schema with a transform or a default describes each direction correctly.

The [`@Signature`](./decorator-signature.mdx) return type is the function data type
the returned function matches — not the raw data type it eventually produces:

| Returned function | Signature return type |
|---|---|
| `(value) => result` | `TRANSFORM<T, R>` |
| `(value) => void` | `CONSUMER<T>` |
| `(value) => boolean` | `PREDICATE<T>` |
| `(a, b) => number` | `COMPARATOR<T>` |
| `() => void` | `RUNNABLE` |

Each returned function is registered under its own identifier, so returning one per
execution never overwrites a function a running flow still holds. A registration has a
maximum lifetime of **30 minutes** and is then dropped from memory — see
[`action.subFlowFunctions`](./sub-flow-function-manager.mdx).

## Error Handling

Throw a `RuntimeError` to signal a recoverable error back to the platform:

```ts
import { RuntimeError } from '@code0-tech/hercules';

run(context: FunctionContext, input: string): string {
  if (!input) throw new RuntimeError('INVALID_INPUT', 'Input must not be empty');
  return input.toUpperCase();
}
```

Mark the function with [`@ThrowsError`](./decorator-throws-error.mdx) so the platform knows to handle the error case.
